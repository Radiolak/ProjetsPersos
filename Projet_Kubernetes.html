Cours et Travaux Pratiques : Orchestration Kubernetes

Source de référence : Kubernetes Basics

1. Fondamentaux du Cluster

Terme / Outil Définition & Rôle Cas d'usage idéal
K8s (Kubernetes) Le projet original "Vanilla". Il regroupe l'ensemble des composants standards, hautement modulaires et configurables de manière indépendante. Datacenters d'entreprise, Cloud public (AWS, GCP) ou infrastructures de production à grande échelle.
K3s Une version ultra-légère certifiée par la CNCF créée par Rancher. Tous les composants K8s sont compilés dans un seul binaire de moins de 100 Mo. Les briques complexes (comme etcd) sont remplacées par défaut par du plus léger (SQLite) mais restent interchangeables. Serveurs à ressources limitées, IoT, serveurs Edge, ou environnements de staging/tests locaux légers.
Minikube / KinD Des outils de simulation locale. Ils démarrent un cluster Kubernetes minimaliste à l'intérieur d'une seule VM ou d'un conteneur Docker sur votre propre poste de travail. Uniquement pour le développement et l'apprentissage rapide sur son PC portable.

Nous allons utiliser K3s car il utilise exactement les mêmes concepts et commandes (kubectl) que le grand K8s, mais s'installe en une seule ligne de commande.

Fonctionnement Déclaratif

Kubernetes fonctionne de manière déclarative :

  1. Vous écrivez un fichier de configuration (manifeste YAML) indiquant l'état souhaité (ex: "Je veux 3 instances de mon application web X, exposées sur le port 80").
  2. Vous envoyez ce fichier au cluster.
  3. Le cluster compare constamment l'état réel du terrain avec l'état souhaité.
  4. Si une VM ou un conteneur crash, Kubernetes s'en aperçoit et le recrée instantanément ailleurs pour respecter votre consigne. C'est le principe d'auto-réparation (Self-Healing).

Architecture du Cluster

Un cluster Kubernetes se divise strictement en deux rôles de serveurs :

Le Control Plane (Les nœuds Masters)

C'est le "cerveau" de l'infrastructure. Il valide et stocke les configurations, et prend les décisions. Il comprend :

  • kube-apiserver : Le point d'entrée unique. Toutes les commandes (kubectl) et toutes les briques internes communiquent exclusivement via cette API REST.
  • etcd : La base de données du cluster. C'est un stockage clé-valeur distribué hautement disponible qui contient toute la configuration et l'état exact du cluster. (Note : K3s utilise SQLite par défaut à la place pour consommer moins de RAM).
  • kube-scheduler : Le répartiteur. Dès que vous demandez à lancer une application, il regarde la RAM/CPU disponible sur vos serveurs Workers et choisit le meilleur endroit où l'exécuter.
  • kube-controller-manager : Les surveillants. Ce sont les boucles de processus qui vérifient constamment que l'état réel correspond à l'état voulu.

Les Workers (Les nœuds d'exécution)

Ce sont les serveurs physiques ou virtuels qui font tourner vos applications. Ils contiennent :

  • Le Container Runtime : Le moteur qui exécute les conteneurs (ex: containerd, Docker).
  • kubelet : L'agent local du Master. C'est un petit démon système qui reçoit les ordres de l'API Server et s'assure que les conteneurs demandés tournent bien localement sur la machine.
  • kube-proxy : Le gestionnaire réseau. Il s’occupe du routage réseau sur chaque nœud, gère le filtrage IP (iptables/IPVS) et permet aux conteneurs de communiquer entre eux ou avec l'extérieur.

Les Objets de Base

  • Pod : La plus petite unité d'exécution. Un Pod encapsule un ou plusieurs conteneurs qui partagent le même réseau et le même stockage. On ne déploie jamais un conteneur brut, on déploie un Pod.
  • Deployment : Le contrôleur de vos Pods. C'est lui qui définit comment déployer l'application (ex: nombre de répliques, stratégie de mise à jour sans coupure).
  • Service : Une IP virtuelle stable (Load Balancer interne). Comme les Pods sont éphémères et peuvent changer d'IP en renaissant, le Service sert de point d'accès réseau fixe pour router le trafic vers les bons Pods.

Orchestration et Scaling

L'un des concepts clés est la gestion par état désiré (Desired State). Le rôle de K8s est de s'assurer en permanence que la réalité correspond à votre configuration YAML.

  1. Le Scaling (Mise à l'échelle) :
    • Scaling horizontal (Out) : Si l'utilisation du processeur (CPU) dépasse un seuil, K8s duplique vos Pods sur d'autres Nodes.
    • Scaling vertical (Up) : Augmenter dynamiquement la RAM ou le CPU alloués à vos Pods existants.
  2. Le Self-Healing (L'auto-guérison) : Si un Pod ne répond plus, le Control Plane le détruit et recrée instantanément un nouveau Pod sain.
  3. Le Load Balancing et Service Discovery : Le Service agit comme une IP fixe et un Load Balancer interne pour distribuer le trafic entre les Pods dont les IP changent constamment.
  4. Les Rolling Updates : Pour mettre à jour une application, Kubernetes déploie la nouvelle version (V2) progressivement, attend qu'elle soit prête, puis redirige le trafic avant de détruire l'ancienne (V1).

Le Projet : Kube-Home

[ INTERNET ] │ ▼ ┌───────────────────────────┐ │ mon-load-balancer │ <-- Répartit le trafic (Load Balancer) └─────────────┬─────────────┘ │ ┌───────────────────┼───────────────────┐ ▼ ▼ ▼ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐ │ Node.js Pod │ │ Node.js Pod │ │ Node.js Pod │ <-- Les 3 Pods de l'application └───────┬───────┘ └───────┬───────┘ └───────┬───────┘ │ │ │ └───────────────────┼───────────────────┘ │ (Hôte: postgres-service) ▼ ┌───────────────────────────┐ │ postgres-service │ <-- Point d'accès stable pour la BDD └─────────────┬─────────────┘ │ ▼ ┌───────────────┐ │ PostgreSQL Pod│ <-- Le Pod de la Base de données └───────┬───────┘ │ ▼ ┌───────────────────┐ │ Persistent Volume │ <-- Les données écrites sur le disque └───────────────────┘

But du projet : Monter un K3s sur une seule VM Linux et tester la création d'un Load Balancer, 3 pods applicatifs, et une base de données PostgreSQL pour tester le scaling horizontal (HPA).

Pré-requis

  • 1 VM Debian (2 Go RAM, 2 vCPUs, 30 Go stockage).

Installation de K3s

# --disable=traefik : Traefik (installé par défaut) occupe déjà le port 80 et bloquerait notre LoadBalancer
# --write-kubeconfig-mode=644 : permet d'utiliser kubectl sans sudo sur la VM (acceptable pour un lab)
curl -sfL https://get.k3s.io | INSTALL_K3S_EXEC="--disable=traefik --write-kubeconfig-mode=644" sh -
sudo kubectl get nodes
kubectl create namespace kube-home

Une fois installé, récupérez le fichier de configuration :

sudo cat /etc/rancher/k3s/k3s.yaml

Dans ce fichier, remplacez server: https://127.0.0.1:6443 par l'adresse IP réelle de votre VM (ex: https://192.168.1.217:6443). Vous pouvez placer ce fichier sur votre PC personnel dans le dossier .kube sous le nom config pour piloter le cluster à distance sans SSH.

TP Partie 1 : Déploiement de l'Infrastructure

Nous allons créer deux fichiers : infrastructure.yaml (Base de données et stockage) et application.yaml (Application Node.js et Load Balancer).

Fichier : infrastructure.yaml

# 1. Le disque dur virtuel pour la persistance
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
---
# 2. Le conteneur PostgreSQL
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:15
          env:
            - name: POSTGRES_PASSWORD
              value: "MonMotDePasseSecret"
          ports:
            - containerPort: 5432
          volumeMounts:
            - name: postgres-storage
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: postgres-storage
          persistentVolumeClaim:
            claimName: postgres-pvc
---
# 3. Le réseau interne
apiVersion: v1
kind: Service
metadata:
  name: postgres-service
spec:
  selector:
    app: postgres
  ports:
    - port: 5432

Fichier : application.yaml

# 1. Les 3 Pods applicatifs
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nodejs-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nodejs-app
  template:
    metadata:
      labels:
        app: nodejs-app
    spec:
      containers:
        - name: nodejs-container
          image: node:18-alpine
          # Sans commande, l'image node lance un REPL qui s'arrête aussitôt (CrashLoopBackOff) : on démarre un mini serveur web sur le port 3000
          command: ["node", "-e", "require('http').createServer((req, res) => res.end('Hello depuis ' + require('os').hostname() + '\\n')).listen(3000)"]
          resources: 
            requests: 
              memory: "128Mi" 
              cpu: "100m" 
            limits:
              memory: "256Mi" 
              cpu: "200m"
          ports:
            - containerPort: 3000
          env:
            - name: DB_HOST
              value: "postgres-service"
            - name: DB_PASSWORD
              value: "MonMotDePasseSecret"
---
# 2. Le Load Balancer
apiVersion: v1
kind: Service
metadata:
  name: mon-load-balancer
spec:
  type: LoadBalancer
  selector:
    app: nodejs-app
  ports:
    - port: 80
      targetPort: 3000

Déploiement et Vérification

# 1. Déploiement de l'infrastructure
kubectl apply -f infrastructure.yaml -n kube-home
 
# 2. Déploiement de l'application
kubectl apply -f application.yaml -n kube-home
 
# Vérification des pods et du stockage
kubectl get pods -n kube-home
kubectl get pvc -n kube-home
kubectl get svc -n kube-home

TP Partie 2 : Sécurisation des données (Secrets)

Problème : Les mots de passe sont en clair dans les fichiers YAML. C'est une faille de sécurité majeure pour Git.

Objectif : Utiliser un objet Secret pour injecter les mots de passe de manière sécurisée.

1. Création du Secret

kubectl create secret generic db-credentials --from-literal=postgres-password='MonMotDePasseUltraSecret123' -n kube-home
  • db-credentials : Nom du coffre-fort.
  • postgres-password : La clé (variable) à l'intérieur.
  • MonMotDePasseUltraSecret123 : La valeur réelle.

2. Mise à jour des fichiers YAML

Dans la section env de vos fichiers infrastructure.yaml et application.yaml, remplacez la ligne value: "..." par :

valueFrom: 
  secretKeyRef: 
    name: db-credentials 
    key: postgres-password

3. Déploiement et Vérification

kubectl apply -f infrastructure.yaml -n kube-home
kubectl apply -f application.yaml -n kube-home
 
# Vérifier le statut
kubectl get pods -w -n kube-home
kubectl get secrets -n kube-home
Attention : PostgreSQL ne lit POSTGRES_PASSWORD qu'à la toute première initialisation du volume. Le PVC contenant déjà une base créée avec l'ancien mot de passe (MonMotDePasseSecret), c'est lui qui reste actif. Pour repartir sur le nouveau : kubectl delete -f infrastructure.yaml -n kube-home (supprime aussi le PVC, donc les données), puis réappliquez le fichier.
Bonnes pratiques : Ne jamais pousser de fichiers contenant des secrets sur Git. Utilisez un .gitignore. Un Secret Kubernetes est seulement encodé en base64, pas chiffré : toute personne ayant accès au namespace peut le lire. En production, utilisez des outils comme Sealed Secrets ou HashiCorp Vault.

TP Partie 3 : Scaling et Load Balancing

Objectifs

  1. Observer le Load Balancing (répartition du trafic).
  2. Scaling Manuel (augmentation de capacité).
  3. Scaling Automatique (HPA).

1. Préparation (Image de test)

Modifiez application.yaml pour utiliser l'image spécialisée qui affiche le nom du Pod :

      containers:
        - name: nodejs-container
          image: paulbouwer/hello-kubernetes:1.10
          resources:          # À conserver : sans "requests" CPU, l'HPA ne peut pas calculer de pourcentage
            requests:
              memory: "128Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "200m"
          ports:
            - containerPort: 8080
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: postgres-password

Cette image écoute sur le port 8080 (et embarque son propre serveur : la ligne command de la Partie 1 n'est plus nécessaire). Dans le Service mon-load-balancer du même fichier, remplacez donc aussi targetPort: 3000 par targetPort: 8080.

Appliquez : kubectl apply -f application.yaml -n kube-home

2. Test du Load Balancing

Lancez cette boucle dans votre terminal pour voir le trafic circuler entre les Pods :

# Remplacez <IP_DE_VOTRE_VM> par l'IP de votre LoadBalancer
while true; do curl -s http://<IP_DE_VOTRE_VM> | grep -o "nodejs-deployment-[a-z0-9-]*" | head -n 1; sleep 0.5; done

3. Scaling Automatique (HPA)

On demande à Kubernetes de créer des Pods si le CPU dépasse 50% :

kubectl autoscale deployment nodejs-deployment --cpu-percent=50 --min=2 --max=10 -n kube-home
kubectl get hpa -n kube-home

4. Défi : Simuler une charge (Stress Test)

Pour déclencher l'HPA, nous allons forcer la consommation CPU d'un Pod :

# 1. Trouver le nom d'un pod
POD_NAME=$(kubectl get pods -n kube-home -l app=nodejs-app -o jsonpath='{.items[0].metadata.name}')
 
# 2. Lancer le stress (CPU à 100%)
kubectl exec $POD_NAME -n kube-home -- /bin/sh -c "while true; do :; done"
 
# 3. Pour arrêter la charge (Ctrl+C ne suffit pas toujours) : supprimer le Pod, le Deployment le recrée
kubectl delete pod $POD_NAME -n kube-home

Observez avec kubectl get hpa -w -n kube-home le nombre de répliques augmenter automatiquement.

TP Partie 4 : Troubleshooting & Maintenance (Le mode Détective)

Objectifs du TP :

  1. Mise à jour (Rolling Update) : Apprendre à changer une version logicielle sans couper le service.
  2. Diagnostic (Troubleshooting) : Utiliser les outils pour comprendre pourquoi une application échoue.
  3. Accès direct (Proxy) : Apprendre à communiquer directement avec un Pod sans passer par le Service.

🚀 Mission 1 : La Mise à jour (Rolling Update)

Dans la vraie vie, on ne réinstalle pas tout pour changer une version. On met à jour le déploiement existant.

L'exercice :

  1. Ouvrez votre fichier application.yaml.
  2. Modifiez l'image de paulbouwer/hello-kubernetes:1.10 vers paulbouwer/hello-kubernetes:1.9 (depuis la Partie 3, c'est cette image qui est utilisée ; la 1.10 étant la dernière publiée, on change simplement de tag).
  3. Appliquez la modification : kubectl apply -f application.yaml -n kube-home.
  4. Observez le processus : Lancez kubectl get pods -w -n kube-home.

Ce que vous devez observer : Kubernetes ne coupe pas tout d'un coup. Il crée un nouveau Pod (V2), attend qu'il soit prêt, puis supprime un ancien Pod (V1). C'est le Rolling Update. Votre application est restée disponible pendant toute l'opération.

🚨 Mission 2 : Le Crash Test (Troubleshooting)

Le scénario : Une erreur de configuration a été introduite. L'application Node.js ne parvient plus à se connecter à la base de données. Votre mission est de trouver la cause exacte.

L'exercice :

  1. Ouvrez application.yaml.
  2. L'image de démo ne se connecte pas réellement à PostgreSQL : changer son mot de passe ne provoquerait aucune erreur. On ajoute donc un initContainer qui teste la connexion à la base avant le démarrage de l'application, avec volontairement un mot de passe différent de celui du Secret. Dans spec.template.spec, juste au-dessus de containers: : 
          initContainers:
        - name: check-db
          image: postgres:15
          command: ["sh", "-c", "psql -h postgres-service -U postgres -c 'SELECT 1'"]
          env:
            - name: PGPASSWORD
              value: "MauvaisMotDePasse"
      containers:
        ...
  3. Appliquez : kubectl apply -f application.yaml -n kube-home.
  4. Le constat : Le nouveau Pod passe en statut Init:Error puis Init:CrashLoopBackOff. Il n'atteint jamais Running. Les anciens Pods, eux, restent Running : le Rolling Update ne supprime pas l'ancienne version tant que la nouvelle n'est pas prête.

Les outils de détective :

Étape A : Regarder l'état global

kubectl get pods -n kube-home

Le statut CrashLoopBackOff signifie que le conteneur démarre, plante, et Kubernetes essaie de le redémarrer en boucle.

Étape B : Analyser les événements (Le "Pourquoi")

# Remplacez <nom-du-pod> par le nom d'un pod en erreur
kubectl describe pod <nom-du-pod> -n kube-home

Regardez la section "Events" en bas du résultat. Vous verrez des messages indiquant si le pod a un problème de montage de volume ou de démarrage.

Étape C : Lire les logs (Le "Quoi")

C'est l'outil le plus puissant. Il permet de lire ce que l'application écrit sur sa console.

# -c cible le conteneur d'init (sinon kubectl répond que le conteneur principal attend de démarrer)
kubectl logs <nom-du-pod> -c check-db -n kube-home

Vous devriez voir un message d'erreur explicite, du type : FATAL: password authentication failed for user "postgres". (Un Connection refused indiquerait plutôt que la base elle-même est injoignable : autre piste.)

Réparation : remplacez value: "MauvaisMotDePasse" par le valueFrom.secretKeyRef de la Partie 2 (db-credentials / postgres-password), puis réappliquez. Le Pod doit passer Running (à condition d'avoir réinitialisé la base comme indiqué en Partie 2).

🔍 Mission 3 : Accès direct via le Proxy

Parfois, le Service (Load Balancer) peut masquer un problème. On veut alors parler directement à un Pod spécifique, sans passer par l'IP du Service.

L'exercice :

  1. Lancez le proxy Kubernetes sur votre machine locale. Ce tunnel permet de communiquer avec l'API du cluster via votre propre PC. 
    kubectl proxy
    (Laissez ce terminal ouvert. Le proxy écoute sur http://localhost:8001).
  2. Ouvrez un deuxième terminal pour récupérer le nom d'un Pod de manière automatique : 
    export POD_NAME=$(kubectl get pods -n kube-home -l app=nodejs-app --field-selector=status.phase=Running -o go-template --template '{{range .items}}{{.metadata.name}}{{"\n"}}{{end}}' | head -n 1)
echo "Nom du Pod ciblé : $POD_NAME"
  3. Accédez au Pod via le tunnel : Utilisez curl pour envoyer une requête directement au Pod en passant par le proxy de l'API : 
    curl http://localhost:8001/api/v1/namespaces/kube-home/pods/$POD_NAME:8080/proxy/
    (Note : On utilise le port 8080 (celui de l'image hello-kubernetes) car on parle directement au conteneur, pas au Service qui lui, écoute sur le 80).
